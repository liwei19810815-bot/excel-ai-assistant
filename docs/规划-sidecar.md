# 规划：sidecar 伴生进程

> 状态：**规划，未开工。有一个必须先由人拍板的安全取舍（见第二节）。**

## 一、它要解决什么

Office.js 有几件事**根本做不到**，不是 API 没做好，是沙箱边界：

| 做不到 | 用户侧的表现 |
|---|---|
| 调用 VBA / 宏 | 工作簿里现成的宏，AI 碰不到 |
| Power Query 刷新与编辑 | "帮我刷新一下数据源"做不了 |
| Power Pivot / OLAP 透视表 | 数据模型类的活全做不了 |
| 文件系统 | 跨文件批处理、按文件夹合并都做不了 |

sidecar 就是一个跑在用户机器上的伴生进程，由它去做这些事，
任务窗格通过本地回环地址调它。

---

## 二、⚠ 先拍板：这道口子值不值得开

**这是本规划里唯一需要人来决定的事，其余都是工程细节。**

sidecar 的本质是：**在用户机器上开一个本地服务，让一个网页能驱动它执行 VBA。**

放在这个项目的上下文里，这个决定很刺眼——我们刚刚因为
「往用户的受信任根存储里装一张根证书会降低他整台机器的防护等级」
而拒绝了装 CA。而 sidecar 打开的口子比那大得多：

### 真正的威胁不是本地恶意软件

本地恶意软件已经拥有用户的全部权限，多一个 sidecar 不改变什么。

**真正的威胁是用户在浏览器里打开的任意网页。**
`127.0.0.1` 对本机所有浏览器进程都是可达的。一个恶意网页可以：

- 直接 `fetch('http://127.0.0.1:PORT/run-vba', {...})`
- CORS 只挡**读响应**，不挡**发请求**。用 `content-type: text/plain`
  的简单请求连预检都不会触发——也就是说，**它读不到结果，但动作已经执行了**

在一个能执行 VBA 的端点上，"只能触发不能读结果"依然是灾难性的。

### 三种可选的安全姿态

| 姿态 | 做法 | 代价 |
|---|---|---|
| **A. 不做 sidecar**（推荐起点） | AI 遇到做不到的事，明确告诉用户"这件事请点工具箱里的 X 按钮" | 零新增攻击面。用户多点一下 |
| **B. 做，但用一次性令牌严格把关** | 见下 | 攻击面可控，但仍然是新增的一个常驻服务 |
| **C. 做，只靠 Origin 校验** | **不可接受** | Origin 挡得住跨域读，挡不住简单请求触发 |

### 姿态 B 的具体设计（如果决定要做）

1. **只绑 `127.0.0.1`**，绝不绑 `0.0.0.0`
2. **随机令牌**：安装时生成 256 位随机串，
   - 写进 sidecar 的本地配置（仅当前用户可读）
   - 同时由安装程序拼进该用户专属 manifest 的 URL：`?sidecar=<token>`
     （和现在注入 `?u=<用户名>` 完全同一条路子，已经验证可行）
   - 任务窗格每次请求都带上它；不带或不对一律 401
   - **远端网页猜不到这个串**，这是整套防护的支点
3. **校验 `Origin`**，只接受网关那个 origin —— 作为第二道，不是唯一一道
4. **白名单式的能力接口**，不做"传一段 VBA 进来执行"这种通用口子。
   只暴露具体动作：刷新查询、列出宏、运行**指定名字**的宏、读文件清单……
5. **每个改动性动作都要任务窗格侧的人工确认**，和 `run_script` 一样
6. **默认不随 Windows 启动**，用完可退出；托盘图标要能一眼看出它在跑
7. **可被治理开关关掉**：复用现有的 `feature.json`，
   IT 能一键禁掉 sidecar 能力，和关 AI 是同一套机制

> 即便如此，这仍然是**新增一个常驻的本地服务**。
> 上线前应当过一遍公司的信息安全评审，而不是由开发单方面决定。

## 三、如果做，技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | **.NET**（或 PowerShell 打包） | 要驱动 Office COM，.NET 最顺；Node 走 COM 要额外的原生模块 |
| 通信 | 本地 HTTP + 令牌 | 任务窗格是网页，只能走 HTTP/WS |
| 端口 | 固定端口 + 冲突时顺延，端口号写进配置 | 随机端口任务窗格找不到；要能被探测 |
| 生命周期 | 托盘程序，用户可见可退出 | **不能是看不见的后台服务**——用户有权知道它在跑 |
| 升级 | 复用工具箱那套共享目录 + 版本化载荷 | 已经验证过的机制，别再造一套 |

### 与现有架构的接缝

- **能力探测**：任务窗格启动时探一次 sidecar 在不在。
  不在就**安静降级**——把 sidecar 类工具从工具列表里摘掉，模型根本看不到它们。
  和现在 `enableRunScript` 关掉时的做法一致。
- **绝不能因为 sidecar 不在就让 AI 不能用。** 这条和"网关挂了任务窗格照常可用"
  是同一条铁律。
- **工具分级**：sidecar 的全部动作归到 `mutate:structure`，一律强制确认。

## 四、实施顺序

| 步 | 内容 | 判据 |
|---|---|---|
| 0 | **安全评审拍板**（第二节） | 有明确结论再往下 |
| 1 | sidecar 骨架：绑回环、令牌校验、健康检查 | 带错令牌必须 401；`0.0.0.0` 探测不到 |
| 2 | 安装集成：生成令牌、写 manifest、写配置 | 复用 `?u=` 那条已验证的路子 |
| 3 | 任务窗格侧：探测 + 降级 | **停掉 sidecar，AI 其余功能完全正常** |
| 4 | 第一个能力：列出并运行工作簿里的宏 | 只能运行**指定名字**的宏，不接受代码 |
| 5 | Power Query 刷新 | |
| 6 | 其余能力 | |

### 测试必须覆盖的

- 带错令牌 → 401
- 不带令牌 → 401
- 从非白名单 Origin → 拒绝
- sidecar 没跑 → 任务窗格正常可用，sidecar 类工具从列表消失
- sidecar 中途挂掉 → 正在进行的对话不崩
- 治理开关关掉 sidecar → 能力立即不可用

## 五、我的建议

**先做姿态 A，把 sidecar 往后放。**

理由：

1. **投入产出比不划算**。VBA 工具箱**已经能做**这些事——60 个命令里
   合并文件夹、批量重命名、导出工作表都在。缺的只是"AI 能不能替你点那个按钮"。
   让 AI 说一句"这件事请点工具箱的「合并文件夹」"，成本几乎为零。
2. **攻击面不成比例**。为了省用户一次点击，新增一个能执行 VBA 的本地服务，
   而且这个项目刚刚因为安全原因拒绝了装根证书这种小得多的事。
3. **真要做，第 0 步是安全评审，不是写代码。**

如果确实需要 Power Query / 数据模型这类**工具箱也做不到**的能力，
那 sidecar 才是唯一出路——那时候再按姿态 B 做，并且过安全评审。
