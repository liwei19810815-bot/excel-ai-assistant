# 规划：sidecar 伴生进程

> 状态：**姿态 B。第 1–5 步已完成，第 6 步第一项能力（调用宏）已完成。**
> 第 1 步实测结论：**Office 可以创建子进程**，启动方式采用首选方案
> （Excel 打开工具箱时由 `.xlam` 拉起）。详见第四节。

## 一、它要解决什么

Office.js 有几件事**根本做不到**，不是 API 没做好，是沙箱边界：

| 做不到 | 用户侧的表现 |
|---|---|
| Power Query 刷新与编辑 | "帮我刷新一下数据源"做不了 |
| Power Pivot / 数据模型 / OLAP 透视表 | 数据模型类的活全做不了 |
| ~~调用 VBA / 宏~~ | ~~工作簿里现成的宏，AI 碰不到~~——**已实现**，见第 6a 步 |
| 文件系统 | 跨文件批处理、按文件夹合并 |

最后一类**工具箱本来就能做**（`merge.folder`、`file.list`、`file.batchRename`、
`file.exportSheets`、`file.insertImages` 五个命令）。

**真正只有 sidecar 能解决的是前三类**——工具箱里精确搜索 `PowerQuery`/
`WorkbookQuery`/`PivotCache`/`ListObjects`，零命中，它也没有这些能力。

## 二、安全约束是怎么来的

方向已定为"做"，但下面这些约束不是可选项，得先说清它们为什么存在。

### 威胁不是本地恶意软件，是用户打开的任意网页

本地恶意软件已经有用户的全部权限，多一个 sidecar 不改变什么。

**`127.0.0.1` 对本机所有浏览器进程都可达。** 用户在浏览器里打开任何一个页面，
那个页面的 JS 就能向 sidecar 发请求。

常见的误解是"有 CORS 挡着"。**CORS 挡的是读响应，不是发请求**：

```js
// 恶意网页里的代码，浏览器不会拦下这个请求
fetch('http://127.0.0.1:8899/run-macro', {
  method: 'POST',
  headers: { 'Content-Type': 'text/plain' },   // 简单请求，不触发预检
  body: '{"name":"某个宏"}'
})
```

请求**会真的发出去、sidecar 会真的执行**，浏览器只是不让那个页面读返回值。
在一个能执行 VBA 的端点上，"能触发但读不到结果"依然是灾难。

> **「内网使用所以风险小」只对一半。** sidecar 只绑回环，本来就不对网络暴露，
> 内网外网一个样。真正的入口是浏览器——只要那台机器能上网、
> 或能访问可能被 XSS 的内网站点，这条路就通。
> 只有**完全禁止浏览器上网**的机器，风险才真的接近零。

### 由此得到的七条约束

1. **只绑 `127.0.0.1`**，绝不 `0.0.0.0`
2. **256 位随机令牌**：安装时生成，写进 sidecar 配置，同时拼进该用户专属
   manifest 的 URL（`?sidecar=<token>`，复用现在注入 `?u=` 那条**已验证可行**的路子）。
   不带或不对一律 401。**远端网页猜不到这个串，这是整套防护的支点**
3. **`Origin` 校验**作为第二道，不是唯一一道
4. **白名单式接口**：只暴露"刷新查询""运行**指定名字**的宏"这类具体动作。
   **绝不做"传一段 VBA 进来执行"的通用口子**——那个口子把风险从"几个动作"
   放大到"任意代码执行"。要什么能力就加一个具体接口
5. 每个**改动性动作**都要任务窗格侧的人工确认（和 `run_script` 一致）
6. 用户**看得见、关得掉**
7. 能被 `feature.json` 治理开关一键禁掉（和关 AI 同一套机制）

**这七条都不牺牲易用性**——令牌用户看不见，只绑回环反而省掉了防火墙弹窗。
安全和简单在这件事上不冲突。

## 三、易用性设计：让用户根本不知道它存在

| 环节 | 做法 | 用户看到什么 |
|---|---|---|
| **安装** | 不单独装，并进现有一键安装包当一个组件（和 AI 组件一样） | 安装时多一个勾选项 |
| **启动** | **Excel 打开工具箱时，由 `.xlam` 用 `Shell()` 拉起** | 什么都没有 |
| **关闭** | 关 Excel 就没了 | 什么都没有 |
| **端口** | 固定端口 + 冲突顺延；任务窗格**带令牌**探一小段范围，认令牌的那个才是自己人 | 什么都没有 |
| **令牌** | 安装时注入 manifest URL + sidecar 配置 | 什么都没有 |
| **防火墙** | 只绑回环 → **Windows 防火墙不弹提示**（弹窗只针对非回环入站） | 什么都没有 |
| **升级** | 复用共享目录 + 版本化载荷（工具箱已验证过的机制），启动时自查 | 什么都没有 |

### 为什么选「Excel 打开时拉起」

这是整套方案里最省事的一点：

- 不用开机自启、不用常驻、不用托盘图标、不用教用户"先启动助手"
- **需要它的时候它正好在，不需要的时候它不存在**
- 安全上也更好：只在用户开着 Excel 的时候活着

**前提是 Office 能创建子进程**——见第四节，这是第 1 步要实测的事。

### 出问题时用户看到什么

**铁律：sidecar 不在 ≠ AI 坏了。**

- 任务窗格照常工作，只是 sidecar 类工具**从工具列表里消失**
  （模型根本看不到它们，不会承诺做不到的事）
- 右上角一个灰点 + 一行小字「本地助手未运行」
- **不弹窗、不报错、不拦着用户用别的功能**

和"网关挂了任务窗格照常可用"是同一条铁律。

## 四、第 1 步：Office 能不能创建子进程（实测）

整个启动方式取决于这一条。企业常部署一条 Defender ASR 规则
**「阻止所有 Office 应用程序创建子进程」**
（GUID `D4F940AB-401B-4EFC-AADC-AD5F3C50688A`），开了它这条路就断。

探测脚本：`Excel Macro/tools/check-office-child-process.ps1`（已交付）

它做两件事：
1. 读 ASR 规则的配置状态（说明性）
2. **真的驱动 Excel 跑一次 VBA `Shell()` 并验证进程确实起来了**（判定性）

> 只看注册表/策略不够——策略可能没下发但被别的机制挡住，
> 也可能配了 Audit 模式（记录但不拦）。**以实际能不能起进程为准。**

判定不止看 `Shell()` 有没有抛错：拿到 PID **不等于**进程起来了，
被拦时的典型表现之一就是"返回了 PID，但进程根本不存在"。
所以脚本会回头按 PID、再按命令行里的一次性 marker 去核实进程真的存在过。
核实不到就判 `INCONCLUSIVE`，**不会当成通过**。

### 怎么在用户机上跑

用户机上几乎都没开「信任对 VBA 工程对象模型的访问」，
所以脚本不能只靠"往工作簿里注入模块"这一条路。两条路都支持：

| 路径 | 用在哪 | 前提 |
|---|---|---|
| 探针加载宏 `AsrProbe.xlam` | **用户机** | 无（不需要 VBOM 信任） |
| 运行时注入模块 | 开发机 | 已开 VBOM 信任 |

操作：先在开发机上跑一次 `-MakeProbe` 生成 `AsrProbe.xlam`
（脚本会当场自检它真能被打开、真能被调用），
把它和脚本一起拷到用户机，在那边直接跑。
`AsrProbe.xlam` 是生成物，**不入库**。

两条路都不可用时脚本判 `INCONCLUSIVE` 并给出操作指引——
**不会因为"没测成"就报成通过。**

### 退出码

| 码 | 含义 |
|---|---|
| 0 | 能起子进程 |
| 1 | 被挡住 |
| 2 | 没测准（含"两条路都不可用"） |
| 3 | 探测本身出错，结论无效 |

四个分支都做过变异验证（把结果强行改坏，确认脚本真的会变红）。

### 结论与退路

| 实测结果 | 启动方式 |
|---|---|
| 能起子进程 | **Excel 打开时由 `.xlam` 拉起**（首选，最省事） |
| 被 ASR 挡住 | 退到**登录时启动**（Startup 文件夹快捷方式，不需要管理员）。代价是变成常驻进程，必须加托盘图标让用户看得见、关得掉 |

**必须在一台真实的用户机器上跑**。开发机通常没有部署企业 ASR 策略，
在开发机上通过不代表用户那边能用。

### 实测结果（第 1 步已完成）

| | |
|---|---|
| 机器 | DESKTOP-RD7D8L3 |
| 日期 | 2026-09-22 |
| 执行路径 | **探针加载宏**——和用户机走的是同一条路，不依赖 VBOM 信任 |
| 结果 | **通过**，退出码 0；VBA `Shell()` 返回 PID 15572，按 PID 核实到该进程确实存在 |
| ASR 规则状态 | 读不到——这台机器没装 Defender（`Get-MpPreference` 不存在） |

**结论：启动方式采用首选方案**——Excel 打开工具箱时由 `.xlam` 拉起，
关 Excel 就退出。不用开机自启、不用常驻、不用托盘图标。

> **这台机器没有部署企业 ASR 策略**，所以这个结果证明的是
> "在不拦的机器上这条路走得通"，**不等于**"在装了 ASR 的机器上也走得通"。
> 退路（登录时启动 + 托盘常驻）因此**不能从设计里删掉**——
> 铺开到一批装了企业策略的机器之前，在那边再跑一次这个脚本。
> 脚本已经交付，随时可跑，成本很低。

### 顺带踩到的坑（写下来免得再踩）

- **`CodeModule.AddFromString` 注入的工程，存成 `.xlam`/`.xlsm` 之后再也打不开**
  （`Workbooks.Open` 抛 `0x800A03EC`），而 `SaveAs` 那一步**不报错**。
  必须走 `VBComponents.Import(.bas)`——这也是 `build.ps1` 一直用 Import 的原因。
- `.bas` 仍然是那两条硬要求：**CRLF + 系统 ANSI**。
- `IsAddin` 必须在 `SaveAs` **之前**置上。
- `.ps1` **必须带 UTF-8 BOM**，否则 Windows PowerShell 按 ANSI 读，中文字符串直接把脚本解析坏。
- PowerShell 里**不能用 `$pid` 当变量名**——那是当前进程的自动变量，
  写进去等于在查脚本自己。

## 五、技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | **.NET** | 要驱动 Office COM，.NET 最顺；Node 走 COM 要额外原生模块 |
| 通信 | 本地 HTTP + 令牌 | 任务窗格是网页，只能走 HTTP/WS |
| 端口 | 固定 + 冲突顺延 | 随机端口任务窗格找不到 |
| 生命周期 | 跟随 Excel（首选）／托盘常驻（退路） | 见第三节 |

### 骨架已落地的部分（第 2 步）

代码在**工具箱仓库**：`Excel Macro/sidecar/ExcelToolboxSidecar.cs`，
构建 `build/build-sidecar.ps1`，回归 `tests/check-sidecar.ps1`（52 条断言）。

> 放在工具箱仓库是因为**发布链路整个在那边**：由 `.xlam` 拉起、
> 由 `Install-Toolbox.ps1` 写配置、由 `pack.ps1` 打进安装包。
> 代价是这份规划文档和它的实现分处两个仓库，改动要同时动两边。

几个定下来的选择：

| 项 | 选择 | 理由 |
|---|---|---|
| 编译器 | **系统自带的 `csc.exe`**，不用 dotnet SDK | 开发机不装 SDK、用户机不装运行时（.NET Framework 4.x 是 Windows 自带的）。代价：**只能写 C# 5 语法** |
| 监听 | **`TcpListener`，不用 `HttpListener`** | `HttpListener` 要 URL 保留（`netsh http add urlacl`），**非管理员拿不到**。开发者在开发机上是管理员，一跑就通，铺到用户机才发现起不来 |
| 令牌位置 | **只认请求头 `X-Toolbox-Token`** | 自定义头强制浏览器预检，远端网页发不出来。**查询串传令牌一律 400**——`?token=` 是简单请求、不触发预检，接受它等于自己把这道门拆了 |
| 令牌比较 | 定长比较 | 普通 `==` 在第一个不同字符处就返回，能被逐位试出来 |
| Origin | 整串相等，不用 `StartsWith` | 否则 `https://gw.corp.example.evil.com` 会被放进来 |
| 配置不合格 | **拒绝启动**（退出码 2） | 没有有效令牌还开端口，等于开了个谁都能用的本机后门 |

配置文件（第 3 步由安装器生成）：

```json
{
  "token": "<64 个十六进制字符 = 256 位>",
  "port": 8899,
  "allowedOrigins": ["https://<网关地址>"]
}
```

> `allowedOrigins` 解析踩过一个坑：`JavaScriptSerializer` 把 JSON 数组
> 反序列化成 `ArrayList` 而**不是** `object[]`，按 `object[]` 去转会得到 null，
> 结果是**白名单静默变空**——配置不报错、进程照常起、`/health` 也正常，
> 只是每个正常来源都被判 403。已修，并有断言守着。

七条变异（令牌改前缀比较、Origin 改 `StartsWith`、CORS 回 `*`、
绑全部网卡、接受查询串令牌、白名单解析退化、去掉父进程守护）
**逐条确认会让套件变红**。

### 第 3–5 步落地情况

**安装（第 3 步）**——都在 `Install-Toolbox.ps1` 里：

- 令牌用 `RandomNumberGenerator` 生成 256 位。**不能用 `Get-Random`**，
  它是可预测的伪随机；令牌被猜到，整套防护的支点就没了。
- 令牌同时写进两个地方，**必须逐字一致**：manifest 的
  `?u=<用户>&sidecar=<令牌>`，以及 `%LOCALAPPDATA%\ExcelToolbox\sidecar\config.json`。
  不一致的表现是任务窗格一直 401，而那个现象看起来像"sidecar 没起来"，
  排查方向会完全跑偏——所以有一条断言专门比对这两个值。
- **sidecar 是可选组件**。分发包里没有 exe 就整段跳过，令牌写空串，
  任务窗格看到空令牌就一个探测请求都不发。
- 装在最后一步，失败连同 manifest 和注册项一起回滚。
- 重装/升级前**先把在跑的 sidecar 停掉**——不停的话 exe 被锁住，覆盖必然失败。

**拉起（.xlam 侧）**——`src/code/Core/modSidecar.bas`，由 `App_Startup` 调用：

- `Shell()` 起进程，传 `--single-instance` 和 `--watch-process EXCEL`
- 单实例：开几个 Excel 也只有一个 sidecar，否则各占一个端口，任务窗格探到谁全看运气
- 跟随宿主：**按"还有没有 EXCEL 进程"判定，而不是盯着拉起它的那一个 PID**。
  盯单个 PID 的话，那个 Excel 先关了 sidecar 就没了，而别的 Excel 还开着——
  表现是"AI 在这个工作簿能用、在那个不能用"
- 整段包在错误保护里：sidecar 起不来只影响几个 AI 能力，
  绝不能把加载宏的启动打断（那是 60 个命令一个都用不了）

**任务窗格（第 4 步）**——`src/store/sidecar.ts`：

- 从 `?sidecar=` 读令牌；**没令牌就一个请求都不发**
- 带令牌探 `127.0.0.1:8899-8903` 的 `/health`，单次超时 1 秒
- **必须校验响应里的 `name`**：那个端口上完全可能是别的程序，
  只要它对任意请求回 200，不校验就会认错人
- 探不到 → `ChatPane` 把 `list_queries` / `refresh_query` 从工具列表摘掉。
  模型看不到就不会承诺做不到的事。不弹窗、不报错，其余功能完全正常

**第一个能力（第 5 步）**——`/queries` 与 `/refresh-query`：

- 刷新**只接受查询的名字**，不接受 M 表达式、不接受任何代码
- COM 用 `Marshal.GetActiveObject` 挂到**用户正开着的** Excel 上。
  自己新开一个的话，刷新的是空白工作簿，用户点了没反应也没报错
- COM 调用放到专用 STA 线程，并且有 60 秒上限——
  Excel 弹着模态对话框时 COM 会一直挂住
- 失败一律如实回（`excel_not_running` / `no_workbook` / `query_not_found` /
  `timeout`）。**最坏的结果是把"没刷新"报成"刷新好了"**，
  用户会拿着旧数据往下做

### 第 6a 步落地情况：调用工作簿里现成的宏

sidecar 三类能力里风险最高的一个——按名字调宏本质上就是让远端指挥本机
执行一段可以做任何事的代码，所以约束比 Power Query 那两个更严：

- **不是"任意宏都能调"，是工作簿作者显式暴露的那些**。sidecar 只认
  `AI_` 开头的 `Sub`；没有这个前缀的宏名，请求在真的去调用 Excel
  **之前**就被拒绝（400），不依赖任何下游失败去兜底。前端也做了一次
  同样的前缀校验，纯粹是为了在请求发出去之前就给出中文提示，
  真正的防线在 sidecar 那边。
- **参数只接受字符串/数字/布尔**，和 `refresh-query` 一样的原则，
  不接受代码或表达式。
- **`/macros`（列出可调用的宏）不是安全边界，只是给用户看的便利**。
  它靠枚举 VBA 工程实现，需要「信任对 VBA 工程对象模型的访问」，
  用户机上大概率没开。枚不出来时如实返回 `trusted:false`，
  **不能说成"没有宏"**——那会让模型断定工作簿里没有可用的宏，
  转而拒绝用户的请求。`/run-macro` 本身不依赖这个信任设置，
  用户知道宏名就能直接调用。
- **`mutate:structure`，一律强制确认**，比 `refresh_query` 更需要——
  刷新查询至少知道"只是拉数据"，宏可以做任何事，唯一的安全边界是
  用户点头。

测试：sidecar 套件新增前缀校验、参数类型校验、失败路径断言；
两条安全断言都做了变异验证（前缀检查失效、参数类型检查失效）确认会变红。
任务窗格侧新增 `runMacro.test.ts`（15 条），覆盖前缀双重校验、
请求内容、以及所有失败分支不能被报成成功。

### 验收评审发现并修掉的（第 6a 步）

独立评审判了**有条件通过**，核心安全边界（`AI_` 前缀、参数类型）确认实现正确，
但挑出一个高危缺口和几个中低优先级问题，全部修掉：

| 严重度 | 问题 | 为什么危险 |
|---|---|---|
| 高 | sidecar **不认"用户是否点了确认"**，只要令牌有效就能直接 `POST /run-macro` | `mutate:structure` 只是任务窗格里的 UI 策略，sidecar 完全不知道这个概念——令牌一旦单独泄露，或允许来源被 XSS/供应链攻击，就能绕过确认弹窗静默执行宏 |
| 中 | `ListMacros` 的正则会把**注释里的伪声明**（`' Sub AI_X(`）当成真宏 | 模型会看到不存在的可调用宏，产生错误调用 |
| 中 | `ListMacros` 正则**漏判跨行 Sub 声明**（VBA 续行符 `_` 出现在名字和括号之间） | 合法的宏因为格式原因枚不出来，模型误以为不存在 |
| 中 | `trusted:false` 的判定**吃掉了所有异常类型**，不只是"没开信任访问" | 把无关的 COM 错误也误判成"未授权"，掩盖了真实故障 |
| 低 | 前端失败分支漏了 `bad_args`/`com_failed`/`missing_name`/`no_result` 等错误码的中文提示 | 不会误报成功，但用户看到的是笼统的"调用失败：xxx"，丢了有用的上下文 |

改法要点：

- **确认下沉到 sidecar**：新增 `/confirm-macro`，用户在任务窗格点了确认之后
  才调用它，换一张绑定"这个宏名 + 这些参数"的一次性、120 秒短时效票；
  `/run-macro` 必须带着与本次调用完全匹配的票才放行，用一次就作废
  （见 `ExcelToolboxSidecar.cs` 里 `_confirmTickets` 那段注释，含设计取舍：
  这挡不住"可信来源自己被 XSS"这种终极场景，但能堵住"普通令牌单独泄露
  就能静默执行"）
- `AiSubPattern` 加 `(?!\s*')` 排除注释行；枚举前先用
  `LineContinuationPattern` 把 VBA 续行拼接成一行再匹配
- `VBProject` 访问只**特定捕获 `COMException`** 才判 `trusted:false`，
  其他异常类型照常向外传，落到 `RunOnSta` 统一的 `com_failed` 分支
- 任务窗格 `runMacro.ts` 补齐 `describeSidecarError`，覆盖 sidecar 能返回的
  全部错误码

新增断言：sidecar 套件 74 → 85（确认票的换取/校验/一次性/参数绑定各种场景）；
任务窗格 `runMacro.test.ts` 15 → 20（两步调用流程、confirm 失败不继续、
补全的错误码分支）。全量回归 409 条断言。

### 验收评审发现并修掉的（第 3–5 步）

独立评审判了**不通过**，五条成立，一条不成立。成立的都改了，并各自补了断言：

| 严重度 | 问题 | 为什么危险 |
|---|---|---|
| 严重 | 安装失败时**只回滚 config.json，不管 exe** | 升级路径上必然发生：留下「新 exe + 旧配置」这种谁也没验证过的组合 |
| 高 | `Stop-RunningSidecar` **按进程名一刀切** | 会杀掉另一份安装、或终端服务器上**别的用户**的 sidecar，对方只看到"本地能力忽然没了" |
| 高 | `ExcelBridge` **只释放 `app`**，其余 RCW 全漏 | `ActiveWorkbook`/`Queries`/`Connections` 都是独立 RCW，漏掉会把 Excel 进程吊住——**用户关了窗口，进程还在后台赖着** |
| 高 | 宿主探测异常被**恒定解释成"宿主还在"** | 查询一直失败时 sidecar **永不退出**，正好违背"关了 Excel 就该没了"这条承诺 |
| 中 | `Content-Length` 非数字时**当成 0** | 请求体被丢掉但请求继续按"无正文"处理，客户端与服务端理解不一致 |

改法要点：

- exe 与 config 一起备份、一起回滚；目录是这次新建且已空则收掉，不留空壳
- 停进程按**完整路径**比对；**读不到路径就不动它**——宁可让升级因文件占用而
  如实失败，也不去杀一个无法确认归属的进程
- COM 对象逐个登记、**逆序 `FinalReleaseComObject`**
- 宿主探测连续失败 30 次（约 1 分钟）就保险起见退出
- `Content-Length` 解析失败 → 400

**不成立的一条**：评审说头部字典区分大小写、小写头会导致 401。
实际用的是 `StringComparer.OrdinalIgnoreCase`（`ExcelToolboxSidecar.cs:789`）。
已补裸 socket 测试，小写、全大写头都实测返回 200。

新增断言：sidecar 套件 52 → 60（HTTP 边界：大小写头、重复令牌头、
畸形/超大 `Content-Length`、超长头部，以及**畸形请求之后服务仍然正常**），
安装器套件 77 → 87（exe 回滚的两种情形、不误杀同名进程）。

> 评审还说"全量回归、vitest、打包"这些结论**未能复现**。那是它那侧的环境限制
> （没有 `git`、文件系统只读、`vitest` 报 `EPERM`），不是结论有误——
> 这些命令在本机可重复跑出同样结果。
